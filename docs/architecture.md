# Balancia architecture

Balancia is a privacy-focused, self-hosted alternative to Splitwise: a single
Next.js application (modular monolith) backed by PostgreSQL, deployable with
one `docker compose up -d --build`.

## System shape

```
┌────────────────────────────────────────────────────────┐
│ Docker Compose                                         │
│                                                        │
│  ┌──────────────────────────────┐  ┌ ─ ─ ─ ─ ─ ─ ─ ─ ┐ │
│  │  app                         │    worker            │
│  │  migrate → Next.js + pg-boss │  │ migrate → pg-boss│ │
│  └──────────────┬───────────────┘   ─ ─ ─ ┬ ─ ─ ─ ─ ─  │
│                 │                        │(profile)    │
│                 └───────────┬────────────┘             │
│                             ▼                          │
│                     ┌──────────────┐  ┌──────────────┐ │
│                     │ PostgreSQL 18│  │ volumes:     │ │
│                     └──────────────┘  │ db-data,     │ │
│                                       │ uploads      │ │
└─────────────────────────────────────  └──────────────┘─┘
```

The default stack is **two containers**: the app runs the background jobs in
its own process, through the `register` hook in `src/instrumentation.ts`. The
`worker` service is a Compose profile, off unless an operator asks for it —
worth asking for when a job is heavy enough to be felt in request latency.

Both application containers run the **same image**; the command selects the
role (`web` or `worker`), and both call the same registrations in
`src/worker/run.ts`, so a queue added there is served whichever shape is
deployed. Each applies pending migrations in its entrypoint before starting,
serialised by a PostgreSQL advisory lock, so there is no separate migration
container to sequence. There are no microservices and no Redis — background
jobs are queued in PostgreSQL through pg-boss.

`RUN_WORKER_IN_WEB` is what selects between the shapes; it defaults to true,
and a deployment that turns the `worker` profile on sets it to false so the two
do not both subscribe. See [environment.md](environment.md#background-jobs).

## Repository layout

- `src/app` — routes, layouts, route handlers, Server Actions. Thin: validate
  input, resolve the actor, call a domain service, render.
- `src/modules/<domain>` — business logic per domain (`auth`, `groups`,
  `participants`, `expenses`, `settlements`, `balances`, `currencies`,
  `recurring`, `imports`, `attachments`, `activity`, `notifications`). Each
  module owns its schemas (zod), services (transaction boundaries), repository
  queries and tests.
- `src/lib/db` — Drizzle schema, client, migration helpers.
- `src/lib/jobs` — pg-boss wiring shared by web and worker processes.
- `src/lib/storage` — receipt storage adapters (local disk, S3-compatible).
- `src/lib/push` — Web Push: VAPID signing and RFC 8291 payload encryption.
- `src/lib/security` — authorization context, guest sessions, rate limiting,
  token hashing, headers.
- `src/components` — presentational and interactive React components.
- `src/worker` — the background jobs. `run.ts` holds the queue subscriptions
  and schedules and is loaded by both shapes; `index.ts` is the standalone
  process wrapper the optional `worker` container runs. Subscriptions only —
  it calls the same domain services as interactive requests.
- `tests` — integration tests (real PostgreSQL) and Playwright journeys.
- `drizzle` — committed SQL migrations (generated by drizzle-kit, reviewed).

### Enforced boundaries

- UI components never query PostgreSQL. Server Components load data through
  module services; domain modules are `server-only` and lint-restricted from
  importing React/Next.
- Route handlers and Server Actions validate input with zod, resolve an
  `Actor` (user session or guest session), authorize through
  `src/lib/security/authorization.ts`, then call services.
- Services own PostgreSQL transactions. Financial writes and their activity
  events commit in the same transaction.
- Repository helpers scope every query by `groupId` — records are never
  fetched by bare ID and authorized afterwards.

| 17  | Web Push implemented on `node:crypto`, no push library                                       | The protocol is a small, fully specified amount of code (ECDH + HKDF + AES-128-GCM, and an ES256 JWT), and it is testable against its own round trip. | 18  | The notifications table is both the inbox and the push outbox                                | The row is written in the change's own transaction, so the inbox can never announce something that rolled back; `pushed_at` is claimed with an UPDATE, which makes delivery exactly-once whether it is the queued job or the sweep that gets there first.                                                                                                                                                                                                                                                                                                 |
| 19  | Sign in with Apple implemented on `node:crypto`, no OIDC client                              | Decision 17 again, and the same maths: one ES256 assertion to sign and one RS256 token to verify against a published key set, testable against its own round trip. | 20  | An Apple identity claims an existing account only when both sides verified the address       | Linking on an email match alone would let anyone who can register with an address they do not own inherit the account of whoever later arrives through Apple — and on an instance with no SMTP, nothing is ever verified, so that is every account. | 21  | Telemetry is a first-party abstraction, not an analytics SDK                                 | An SDK would be a dependency with the ability to send whatever it liked, and its presence would make "we collect nothing by default" a claim about somebody else's code. | 22  | No installation identifier, and the retention analytics that would need one are given up     | An identifier that persists across reports is the difference between statistics and a record of a particular server, and every system that has one eventually finds a reason to join something to it. | 23  | The telemetry collector is the same application in a different role                          | `TELEMETRY_RECEIVER=true` is the whole of it. | 24  | Local metrics are a hand-written Prometheus exposition, not a metrics library                | Decision 17 again: the text format is short and fully specified, and the audience is one operator scraping their own server. The rule that pays for itself is that every label value is a literal from the source — a route template, a queue name — so no identifier can reach a label and cardinality is bounded by construction.                                                                                                                                                                                                                       |
| 25  | The first registered account is the instance administrator                                   | Telemetry is the first setting Balancia has had that belongs to the whole installation rather than to a group, and there was no role for it. On a self-hosted deployment the first account is the operator's, so it claims the flag inside its own INSERT; there is no way to ask for it and no UI that grants it. Group ownership grants nothing here — the owner of a group is not the owner of the server.                                                                                                                                             |
| 26  | Onboarding asks for identity only; everything else is asked after the balance is on screen   | Each field in front of an account costs completions, and currencies, notation, notifications and payout details are all answerable later — several of them better later, at the moment they pay off. They live on a skippable "Finish setting up" list instead. The route through onboarding is derived from the arrival rather than stored, because a hand-maintained screen order is where this goes wrong.                                                                                                                                             |
| 27  | A passkey signup creates the account only once the authenticator has answered                | The obvious order — write the user, then attach the credential — leaves an abandoned ceremony owning an email address with no password and no passkey, which nobody can sign in to and nobody else can register. So the pending name and address wait on the `webauthn_challenges` row, which already expires in five minutes and is already single-use, and the account and its first credential are written in one transaction.                                                                                                                         |
| 28  | Six-digit codes are never looked up by their own hash, and are rate limited per address      | A link token carries 256 bits and can be found by its digest; a code carries under twenty and cannot. The account is established first and the code checked against that account alone, its digest is peppered with the account id so the hash of `000000` matches no row, the comparison is timing-safe, and attempts are capped per address rather than per IP so nobody can spend a stranger's allowance. A code-only account can sign in with a code, which is no weaker than the password reset that already turns inbox access into account access. |
| 29  | A payment QR is built for the account's own scheme, or not at all                            | The Swiss QR-bill and the EPC Girocode do not compete: a Swiss banking app reads the first and not the second, and the rest of SEPA the other way round, so the IBAN's country decides and there is no fallback between them. Refusing is the common case and a real answer — a Swiss account with no address on file, a QR-IBAN whose bank issues per-invoice references nobody here can mint, a debt in a currency neither standard carries. What people do with a payment QR is trust it, so one that cannot be built correctly is not built.          |

## Domain model (overview)

- **Identity**: `users` (scrypt `password_hash`, nullable so an account can be
  passkey-only), `sessions` (random token, only its SHA-256 hash stored),
  `passkeys` (WebAuthn credential, public key and signature counter),
  `webauthn_challenges` (server-issued, single-use, five-minute lifetime; a
  `signup` challenge also carries the name and address of the account it will
  create, so that an abandoned ceremony leaves nothing behind rather than an
  address owned by a row with no credential),
  `verification_tokens` (email confirmation, password reset, email change, and
  the two six-digit codes, all hashed; an email change carries its target
  address on the token rather than on the account, so an unconfirmed request
  leaves nothing behind) and
  `oauth_identities` (an external provider's stable subject, unique per
  provider, so an account can have a password, passkeys, an Apple link, or any
  combination).
  `payout_methods` (per account, ordered, one row per method) says how somebody
  wants to be paid back; it is read only for people the reader owes money to,
  and never included in a group export, because it belongs to the person rather
  than to the trip.
  `participants` are group-scoped identities, optionally linked to a user
  (`user_id` nullable). Guests are participants without a linked user who
  authenticate through invite tokens → guest sessions.
- **Groups**: `groups` (currency mode `separate` | `converted`, optional base
  currency, timezone, archived timestamp) and `group_members`
  (owner/member roles) for registered users.
- **Expenses**: `expenses` + `expense_payers` (multiple payers) +
  `expense_shares` (final integer allocations, plus the original split input
  metadata so edits can restore the chosen method). Soft-deleted via
  `deleted_at`. Converted groups freeze `exchange_rate`, its source and
  timestamp, and the deterministically rounded converted amount.
- **Settlements**: dedicated `settlements` table (payer → recipient, amount,
  currency, optional conversion) — they affect balances but are not expenses.
- **Recurring**: `recurring_expenses` templates + `recurring_occurrences`
  uniqueness table that makes generation idempotent.
- **Imports**: `import_runs` + `import_rows` staging with row fingerprints for
  duplicate-free retry.
- **Attachments**: `attachments` metadata (storage key, MIME, size, checksum);
  binary content lives in the storage adapter.
- **Categorization**: `expense_category_mappings` remembers the category a
  group or a user chose for a merchant, written in the same transaction as the
  expense that taught it. The rules themselves are code
  (`src/modules/categorization`), not data — see `docs/categorization.md`.
- **Receipt scanning**: no schema at all. Reading a receipt is a browser-side
  operation whose output is a proposal, and the only thing persisted is the
  expense the user confirms — plus, if they ask for it, the image through the
  ordinary attachment flow. The rules are code (`src/modules/receipts`) and the
  models are operator-installed files — see `docs/receipt-scanning.md`.
- **Activity**: append-only `activity_events` written in the same transaction
  as the financial change.
- **Notifications**: `notifications` is one row per person told about one
  event — the in-app inbox, and the outbox push delivery claims through
  `pushed_at`. `push_subscriptions` holds the browsers that agreed to receive
  push; `notification_preferences` and `notification_group_mutes` are the two
  switches, and both suppress the row rather than hiding it after the fact.
  Only registered users are reachable: a guest is a link holder with no
  account, so an unlinked participant is simply not a recipient.
- **Exchange rates**: `exchange_rate_quotes` caches what an optional external
  provider answered, per (provider, base, quote, day). It is a cache and
  nothing more — every rate that matters is frozen on its expense, so the table
  can be emptied without moving a single balance.

## Balance engine

`src/modules/balances` derives net positions per participant from payer
contributions, expense shares and settlements — deleted expenses excluded.
`separate` groups produce one balance list per currency; `converted` groups
produce base-currency balances. The engine guarantees Σ(balances) = 0 per
currency and produces a deterministic greedy simplification (largest debtor →
largest creditor) that is presentation-only: it never alters recorded history.

## Security model

- Central authorization: every group-scoped read/mutation resolves the actor
  (user membership or guest session participant) before touching data;
  queries are scoped by the authorized group ID.
- Authentication: scrypt password hashing (N=2¹⁷, r=8, p=1) from Node's
  standard library; sign-in is constant-time with respect to account existence
  and returns one message for every credential failure. Session and invitation
  tokens are 256-bit random values stored only as SHA-256 hashes.
- CSRF: Server Actions are origin-checked by Next.js, `proxy.ts` adds an origin
  check for route handlers, and cookies are `HttpOnly`, `SameSite=Lax`,
  `Secure` when the public URL is HTTPS.
- Two kinds of invite link, with deliberately different power. A _guest
  invitation_ names one participant: holding it means acting as that person, so
  it is exchanged at `/join/[token]` for a separate guest-session token and the
  link can be revoked independently of the sessions derived from it. A _group
  join link_ (`group_join_links`) names only a group, so whoever opens it has
  not been identified yet; `/join/g/[token]` puts that token straight into a
  short-lived cookie and every read re-resolves it by hash, which means
  revoking the link ends every in-flight join at once because no derived
  credential outlives it. Both leave the token out of the address bar, history
  and referrers by redirecting to a token-free URL.
- The group join link is the one token stored in a form the server can read
  back, because group settings has to show the live link weeks after minting it
  — a link that can only be seen once has to be replaced to be shared with a
  sixth person, invalidating it for the five who already have it. Lookups are
  still by SHA-256 hash; alongside the hash sits an AES-256-GCM ciphertext
  under a key derived from `AUTH_SECRET` by HKDF (`lib/security/secret-box.ts`),
  so a dump of the database alone still yields no working links. A ciphertext
  that does not open — rotated secret, edited row, a link minted before the
  column existed — reads as "cannot be shown", never as an error.
- Claiming a name is decided by the database, not by a prior read: the link
  from participant to user account is an `UPDATE … WHERE user_id IS NULL`, so
  two people racing for the same name cannot both be told they won.
- Rate limiting: PostgreSQL-backed fixed-window limiter on sign-in,
  registration, password reset, email change and both kinds of link redemption.
  The email-change bucket is keyed by account rather than by client address,
  because what it spends is mail to an inbox the caller chose.
- Account recovery and email change: single-use hashed tokens, opened from a
  link, spent by a route handler so the token is consumed exactly once and does
  not survive into the address bar. A reset ends every session; an email change
  is announced to the old address at request time, before it can take effect,
  and only completes when the new address is confirmed. Neither is offered on
  an instance with no SMTP configured.
- Strict security headers + CSP via `proxy.ts` (Next 16's middleware
  replacement).
- Uploads: content-sniffed MIME allowlist (JPEG/PNG/WebP/GIF/PDF), size
  limits, random object names, authorization on download, no public uploads
  directory.
- WebAuthn: explicit `WEBAUTHN_RP_ID`/origin configuration validated at boot;
  HTTPS required outside localhost.
- Instance administration: `users.is_admin`, held by the first account
  registered. It governs deployment-wide settings only — today, telemetry — and
  grants nothing inside anybody's group.

## Telemetry and metrics

Two separate systems, neither of which is on by default:

- **Product telemetry** (`src/lib/telemetry`) records typed events as local
  counters, and — only if an administrator opts in — sends one bucketed
  weekly report with no installation identifier. `docs/telemetry.md` is the
  complete field list and the reasoning.
- **Operational metrics** (`src/lib/metrics`) are exact, local and never
  transmitted: Prometheus text at `/api/metrics`, off unless the operator asks
  for it.

See `docs/` for self-hosting, backup/restore, environment reference, telemetry
and data migration guides.
