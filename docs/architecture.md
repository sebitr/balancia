# Balancia architecture

Balancia is a privacy-focused, self-hosted alternative to Splitwise: a single
Next.js application (modular monolith) backed by PostgreSQL, deployable with
one `docker compose up -d --build`.

## System shape

```
┌────────────────────────────────────────────────────────┐
│ Docker Compose                                         │
│                                                        │
│  ┌────────────────────┐   ┌────────────────────┐       │
│  │  app               │   │  worker            │       │
│  │  migrate → Next.js │   │  migrate → pg-boss │       │
│  └─────────┬──────────┘   └─────────┬──────────┘       │
│            │                        │                  │
│            └───────────┬────────────┘                  │
│                        ▼                               │
│                ┌──────────────┐   ┌──────────────────┐ │
│                │ PostgreSQL 18│   │ volumes:         │ │
│                └──────────────┘   │ db-data, uploads │ │
└────────────────────────────────────┴──────────────────┴┘
```

Both application containers run the **same image**; the command selects the
role (`web` or `worker`). Each applies pending migrations in its entrypoint
before starting, serialised by a PostgreSQL advisory lock, so there is no
separate migration container to sequence. There are no microservices and no
Redis — background jobs are queued in PostgreSQL through pg-boss.

## Repository layout

- `src/app` — routes, layouts, route handlers, Server Actions. Thin: validate
  input, resolve the actor, call a domain service, render.
- `src/modules/<domain>` — business logic per domain (`auth`, `groups`,
  `participants`, `expenses`, `settlements`, `balances`, `currencies`,
  `recurring`, `imports`, `attachments`, `activity`, `notifications`). Each
  module owns its schemas (zod), services (transaction boundaries), repository
  queries and tests.
- `src/lib/db` — Drizzle schema, client, migration helpers.
- `src/lib/jobs` — pg-boss wiring shared by web and worker processes.
- `src/lib/storage` — receipt storage adapters (local disk, S3-compatible).
- `src/lib/push` — Web Push: VAPID signing and RFC 8291 payload encryption.
- `src/lib/security` — authorization context, guest sessions, rate limiting,
  token hashing, headers.
- `src/components` — presentational and interactive React components.
- `src/worker` — worker entrypoint (pg-boss subscriptions only; it calls the
  same domain services as interactive requests).
- `tests` — integration tests (real PostgreSQL) and Playwright journeys.
- `drizzle` — committed SQL migrations (generated by drizzle-kit, reviewed).

### Enforced boundaries

- UI components never query PostgreSQL. Server Components load data through
  module services; domain modules are `server-only` and lint-restricted from
  importing React/Next.
- Route handlers and Server Actions validate input with zod, resolve an
  `Actor` (user session or guest session), authorize through
  `src/lib/security/authorization.ts`, then call services.
- Services own PostgreSQL transactions. Financial writes and their activity
  events commit in the same transaction.
- Repository helpers scope every query by `groupId` — records are never
  fetched by bare ID and authorized afterwards.

| 1   | Next.js 16 App Router, Turbopack builds                                                      | Current stable; Server Components load data on the server, client JS stays small.                                                                                                                                                                                                                                                                                             |
| 2   | Modular monolith, one image, role-per-command                                                | Self-hosting simplicity; no service mesh to operate.                                                                                                                                                                                                                                                                                                                          |
| 3   | Money as integer minor units (`bigint` in PostgreSQL and TypeScript)                         | No floating point for money, ever. | 4   | Exchange rates as PostgreSQL `numeric`, decimal.js in application code                       | Exact decimal arithmetic; rates are frozen per expense, never recalculated retroactively.                                                                                                                                                                                                                                                                                     |
| 5   | Largest-remainder allocation with stable participant ordering                                | Deterministic splits that always sum exactly to the total.                                                                                                                                                                                                                                                                                                                    |
| 6   | First-party authentication: scrypt passwords, hashed DB sessions, own WebAuthn state machine | A self-hosted app must not depend on an auth vendor with a commercial tier. Only the WebAuthn _protocol_ (CBOR/COSE, signature verification) is delegated, to `@simplewebauthn/server` — MIT, no paid tier.                                                                                                                                                                   |
| 7   | Guest access via opaque 256-bit invite tokens, only SHA-256 hashes stored                    | Link holders act as the invited participant; tokens are revocable, optionally expiring, rate limited, and never logged.                                                                                                                                                                                                                                                       |
| 8   | pg-boss (PostgreSQL-backed) for recurring expenses and imports                               | Background processing without Redis; idempotency via a unique `(recurring_expense_id, occurrence_date)` constraint.                                                                                                                                                                                                                                                           |
| 9   | Drizzle ORM + drizzle-kit with committed SQL migrations                                      | Reviewed migrations applied by the image entrypoint at startup, serialised by an advisory lock; no schema push in production.                                                                                                                                                                                                                                                 |
| 10  | Serwist in “configurator” mode (`serwist build` after `next build`)                          | Turbopack-compatible PWA build; the service worker never caches auth endpoints or mutations.                                                                                                                                                                                                                                                                                  |
| 11  | Storage adapter interface with local-disk default, optional S3 driver                        | Receipts persist in a named volume; metadata in PostgreSQL, binary content on disk/S3.                                                                                                                                                                                                                                                                                        |
| 12  | Secrets generated into `.env` by `scripts/bootstrap.sh`, not baked in                        | No fixed shared secret ships in the repository, and the operator holds the only copy in a file they can see and back up.                                                                                                                                                                                                                                                      |
| 13  | pino structured logs with redaction; no external telemetry                                   | Privacy by default; correlation IDs for requests/jobs/imports.                                                                                                                                                                                                                                                                                                                |
| 14  | AGPL-3.0-or-later                                                                            | Network copyleft matches the self-hosted, community-owned goal.                                                                                                                                                                                                                                                                                                               |
| 15  | Husky/lint-staged omitted                                                                    | CI runs lint/typecheck/tests on every push; local git hooks add setup friction without adding safety.                                                                                                                                                                                                                                                                         |
| 16  | Categorization is deterministic rules first, an optional local model second                  | Rules answer instantly, are readable, testable and extensible in a data file, and need no download. The embedding model is opt-in, runs in the browser against files this instance serves, and never decides alone.                                                                                                                                                           |
| 17  | Web Push implemented on `node:crypto`, no push library                                       | The protocol is a small, fully specified amount of code (ECDH + HKDF + AES-128-GCM, and an ES256 JWT), and it is testable against its own round trip. A dependency here would add a supply chain to audit for ~200 lines. Payloads are encrypted end to end, so the relaying push service never sees content.                                                                 |
| 18  | The notifications table is both the inbox and the push outbox                                | The row is written in the change's own transaction, so the inbox can never announce something that rolled back; `pushed_at` is claimed with an UPDATE, which makes delivery exactly-once whether it is the queued job or the sweep that gets there first.                                                                                                                     |
| 19  | Sign in with Apple implemented on `node:crypto`, no OIDC client                              | Decision 17 again, and the same maths: one ES256 assertion to sign and one RS256 token to verify against a published key set, testable against its own round trip. A general OIDC client brings discovery, session handling and a dozen grant types nothing here uses. The algorithm is pinned rather than read from the token, which is what the alg-confusion attacks need. |
| 20  | An Apple identity claims an existing account only when both sides verified the address       | Linking on an email match alone would let anyone who can register with an address they do not own inherit the account of whoever later arrives through Apple — and on an instance with no SMTP, nothing is ever verified, so that is every account. The fallback is to sign in as you already can and link deliberately, which needs no trust in the match at all.            |

## Domain model (overview)

- **Identity**: `users` (scrypt `password_hash`, nullable so an account can be
  passkey-only), `sessions` (random token, only its SHA-256 hash stored),
  `passkeys` (WebAuthn credential, public key and signature counter),
  `webauthn_challenges` (server-issued, single-use, five-minute lifetime),
  `verification_tokens` (email confirmation and password reset, hashed) and
  `oauth_identities` (an external provider's stable subject, unique per
  provider, so an account can have a password, passkeys, an Apple link, or any
  combination).
  `participants` are group-scoped identities, optionally linked to a user
  (`user_id` nullable). Guests are participants without a linked user who
  authenticate through invite tokens → guest sessions.
- **Groups**: `groups` (currency mode `separate` | `converted`, optional base
  currency, timezone, archived timestamp) and `group_members`
  (owner/member roles) for registered users.
- **Expenses**: `expenses` + `expense_payers` (multiple payers) +
  `expense_shares` (final integer allocations, plus the original split input
  metadata so edits can restore the chosen method). Soft-deleted via
  `deleted_at`. Converted groups freeze `exchange_rate`, its source and
  timestamp, and the deterministically rounded converted amount.
- **Settlements**: dedicated `settlements` table (payer → recipient, amount,
  currency, optional conversion) — they affect balances but are not expenses.
- **Recurring**: `recurring_expenses` templates + `recurring_occurrences`
  uniqueness table that makes generation idempotent.
- **Imports**: `import_runs` + `import_rows` staging with row fingerprints for
  duplicate-free retry.
- **Attachments**: `attachments` metadata (storage key, MIME, size, checksum);
  binary content lives in the storage adapter.
- **Categorization**: `expense_category_mappings` remembers the category a
  group or a user chose for a merchant, written in the same transaction as the
  expense that taught it. The rules themselves are code
  (`src/modules/categorization`), not data — see `docs/categorization.md`.
- **Receipt scanning**: no schema at all. Reading a receipt is a browser-side
  operation whose output is a proposal, and the only thing persisted is the
  expense the user confirms — plus, if they ask for it, the image through the
  ordinary attachment flow. The rules are code (`src/modules/receipts`) and the
  models are operator-installed files — see `docs/receipt-scanning.md`.
- **Activity**: append-only `activity_events` written in the same transaction
  as the financial change.
- **Notifications**: `notifications` is one row per person told about one
  event — the in-app inbox, and the outbox push delivery claims through
  `pushed_at`. `push_subscriptions` holds the browsers that agreed to receive
  push; `notification_preferences` and `notification_group_mutes` are the two
  switches, and both suppress the row rather than hiding it after the fact.
  Only registered users are reachable: a guest is a link holder with no
  account, so an unlinked participant is simply not a recipient.
- **Exchange rates**: `exchange_rate_quotes` caches what an optional external
  provider answered, per (provider, base, quote, day). It is a cache and
  nothing more — every rate that matters is frozen on its expense, so the table
  can be emptied without moving a single balance.

## Balance engine

`src/modules/balances` derives net positions per participant from payer
contributions, expense shares and settlements — deleted expenses excluded.
`separate` groups produce one balance list per currency; `converted` groups
produce base-currency balances. The engine guarantees Σ(balances) = 0 per
currency and produces a deterministic greedy simplification (largest debtor →
largest creditor) that is presentation-only: it never alters recorded history.

## Security model

- Central authorization: every group-scoped read/mutation resolves the actor
  (user membership or guest session participant) before touching data;
  queries are scoped by the authorized group ID.
- Authentication: scrypt password hashing (N=2¹⁷, r=8, p=1) from Node's
  standard library; sign-in is constant-time with respect to account existence
  and returns one message for every credential failure. Session and invitation
  tokens are 256-bit random values stored only as SHA-256 hashes.
- CSRF: Server Actions are origin-checked by Next.js, `proxy.ts` adds an origin
  check for route handlers, and cookies are `HttpOnly`, `SameSite=Lax`,
  `Secure` when the public URL is HTTPS.
- Rate limiting: PostgreSQL-backed fixed-window limiter on sign-in,
  registration and guest-token redemption.
- Strict security headers + CSP via `proxy.ts` (Next 16's middleware
  replacement).
- Uploads: content-sniffed MIME allowlist (JPEG/PNG/WebP/GIF/PDF), size
  limits, random object names, authorization on download, no public uploads
  directory.
- WebAuthn: explicit `WEBAUTHN_RP_ID`/origin configuration validated at boot;
  HTTPS required outside localhost.
